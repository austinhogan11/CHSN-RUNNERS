# Runner V1.1: Native iOS / Mobile Support

Runner V1.1 shipped in September 2026. It adds a native iOS client to the
production Runner system while preserving the web application and the existing
backend workout contract. The production web client remains available at
[chosenrunning.com](https://chosenrunning.com). This document records V1.1 as it
shipped; later behavior belongs in a new release file.

## Release Summary

V1.0 established the production web path:

```text
Runner Web → Runner API → DynamoDB
```

V1.1 makes Runner a multi-client product:

```text
Runner Web ─┐
            ├→ shared Runner API → shared DynamoDB persistence
Runner iOS ─┘
```

The milestone is architectural as well as visual: both clients use one backend
contract, one Clerk identity model, and one source of truth. The iOS app does
not introduce a mobile-specific backend or duplicate workout persistence.

## Native Product Experience

The SwiftUI application provides a native Runner dashboard with:

- an actual-mileage trend backed by 52 weeks of API data and a 12-week visible
  window
- navigation through historical 12-week trend windows
- selectable mileage points with exact week and mileage details
- week-over-week mileage comparison for the selected point
- a current 12-week average compared with the preceding trend window
- Monday-through-Sunday workout navigation for past, current, and future weeks
- a seven-day overview and full selected-day workout detail
- support for multiple workouts on the same day
- workout creation, editing, and confirmed deletion
- distance, duration, derived pace, optional start time, and weekly mileage,
  duration, and workout-count totals
- initial, navigation, mutation, authentication, transport, and API error states
- native hosted sign-in and sign-out

The workout editor changes the fields exposed by the V1.1 mobile experience:
title, actual distance, duration, and start time. Pace is derived from positive
distance and duration rather than entered or stored separately. Existing workout
types, descriptions, planned distance, and server status remain readable through
the shared contract, but V1.1 does not expose all of them as mobile editor fields.

The backend's existing completion semantics remain authoritative. A workout has
actual execution when actual distance or duration is non-null. Clearing both
returns the workout to planned. Null continues to mean unknown or not supplied;
zero values received from the API remain distinct during transport and mapping.

## Shared Data and API Boundary

Both clients read and mutate the same user-owned records through FastAPI. The
iOS production boundary is `https://chosenrunning.com/api`; the web client uses
the equivalent relative `/api` path through CloudFront.

The native app uses these authenticated operations:

- `GET /api/weeks/{day}`
- `GET /api/trends/mileage`
- `POST /api/workouts`
- `PATCH /api/workouts/{workout_id}`
- `DELETE /api/workouts/{workout_id}`

The iOS app never connects directly to DynamoDB. FastAPI remains the authority
for validation, completion state, authentication, ownership, and persistence.
Web and iOS changes become visible to the other client through normal API reads;
V1.1 does not add real-time push synchronization.

Authenticated production create, edit, and delete behavior was manually checked
across iOS and web as part of the V1.1 release validation.

## Native Architecture

```text
SwiftUI views
    ↓
DashboardState
    ↓
WorkoutRepository
   ↙          ↘
InMemory      APIWorkoutRepository
                  ↓
               APIClient
                  ↓
              Runner API
```

- SwiftUI views render authentication, trends, week navigation, selected-day
  sessions, weekly totals, and workout forms.
- `DashboardState` orchestrates loading, selection, navigation, mutations,
  refresh after confirmed mutations, and user-facing error state.
- `WorkoutRepository` separates product state from persistence. The in-memory
  implementation supports previews and deterministic tests; the API
  implementation is used by the production app.
- `APIClient` uses `URLSession` with Swift concurrency and `Codable` request and
  response DTOs.
- Explicit DTO-to-domain mapping preserves backend workout IDs as strings and
  keeps transport naming separate from native models.
- Calendar-only dates and wall-clock start times are parsed with the Runner
  calendar rather than treated as UTC timestamps.
- Optional execution fields preserve the backend distinction between null and
  a numeric zero. Native workout input normalizes non-positive user-entered
  distance and duration to an absent execution value.

## Authentication and Ownership

Runner iOS uses ClerkKit with the same Clerk identity system as the web client.
The application bundle identifier is `com.chosenrunning.app`.

ClerkKit opens the hosted authentication flow and manages the native session.
`ClerkAccessTokenProvider`, behind the app's `AccessTokenProvider` abstraction,
retrieves the current Clerk session token. `APIClient` sends it to Runner as:

```text
Authorization: Bearer <session token>
```

FastAPI continues to verify the Clerk-issued JWT and derive the storage owner
from its `sub` claim. All week, trend, create, update, and delete operations use
that verified identity. The native client cannot choose a different user ID,
and no authentication bypass was added. Sign-out clears the Clerk session and
returns the application to the signed-out experience.

No publishable-key value, session token, certificate, or signing credential is
part of this release record.

## Mobile CI and Validation

The tracked iOS GitHub Actions workflow runs when iOS or workflow files change
in pull requests and on pushes to `main`. It uses a GitHub-hosted macOS runner
and grants the workflow token read-only repository-content access.

CI performs the following sequence:

1. Select Xcode and an available iPhone simulator.
2. Resolve Swift package dependencies.
3. Run `xcodebuild build-for-testing`.
4. Run the permanent `Runner.xctestplan` with
   `xcodebuild test-without-building`.

Both Xcode phases set `CODE_SIGNING_ALLOWED=NO`, so pull-request CI does not need
an Apple signing certificate or App Store secret.

The permanent suite covers:

- Clerk token-provider success, absence, and failure behavior
- bearer-token injection and HTTP, decoding, and transport failures
- deterministic networking through a stubbed `URLProtocol`
- API DTO decoding and explicit transport-to-domain mapping
- backend string IDs, local date/time conversion, nulls, zeroes, and planned
  values
- in-memory repository CRUD and aggregation
- Monday-based calendars, weekly mileage, pace, multi-workout selected days,
  week navigation, trend windows, trend selection, and chart scale behavior
- live dashboard orchestration for loading, navigation, backend-authoritative
  mutation refresh, authentication failures, and recoverable errors

The suite is intentionally described by coverage rather than a fixed test count.
Manual release validation included a physical-device build and launch, hosted
Clerk sign-in on an iPhone, an authenticated production week load, and iOS-to-web
create, edit, and delete synchronization.

## V1.1 Boundary

V1.1 delivers a native client for the existing Runner workout workflow. It does
not include:

- GPS or Core Location activity recording
- MapKit route visualization, elevation, or an activity-route model
- HealthKit or Apple Watch support
- background activity recording
- an offline-first synchronization engine or local persistent database
- push notifications
- Android support
- advanced training-plan generation

These remain possible later work and are not commitments for a particular next
release.

## Known Limitations and Distribution Readiness

Implemented product behavior and App Store readiness are separate. At the V1.1
snapshot:

- Cross-client data is server-mediated and eventually visible on the next API
  load. The iOS dashboard has no pull-to-refresh control or real-time update
  channel.
- Expired-session behavior has deterministic state coverage, but still needs a
  recorded end-to-end manual check with a naturally expired Clerk session.
- The interface includes targeted accessibility labels and scalable layouts,
  but comprehensive small-device, Dynamic Type, VoiceOver, and accessibility
  validation is not recorded.
- The Xcode target still reports marketing version `1.0`; release metadata must
  be aligned before a V1.1 App Store archive.
- App Store archive/signing validation and TestFlight smoke testing are not
  recorded as complete.
- There is no TestFlight or App Store distribution automation in the repository.
- Production still uses the existing Clerk development instance documented for
  V1; migration to a Clerk production instance remains deferred.
