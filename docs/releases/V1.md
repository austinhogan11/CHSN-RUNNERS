# Runner V1

Runner V1 shipped in September 2026 and is available at
[chosenrunning.com](https://chosenrunning.com). This document records V1 as it
shipped; later behavior belongs in a new release file.

## Product

V1 is an authenticated running log for planning workouts, recording execution,
and reviewing actual weekly mileage.

Each training week runs Monday through Sunday. A runner can move through past
and future weeks without a fixed navigation limit and return directly to the
current week. Empty future and past weeks remain usable for scheduling.

The weekly workout experience combines two views:

- a compact seven-day overview showing dates, combined displayed mileage, and
  the current/selected day
- a selected-day detail panel containing that day's sessions and creation,
  editing, and deletion controls

Multiple sessions can share a calendar date. Missing sessions are presented as
empty days and are not persisted as fake rest workouts. Explicit rest sessions
remain valid workout records.

Runners can create sessions, edit displayed workout fields directly, and delete
sessions after confirmation. Updates save through authenticated partial-update
requests. Average pace is derived from duration and positive actual distance;
it is not independently entered or stored.

## Completion Semantics

A workout is treated as executed when it has a non-null actual distance or a
non-null duration. Clearing both execution fields returns it to planned. The
persisted status remains part of the API and storage model for compatibility and
is normalized when execution data changes, but the primary V1 interface does
not expose a separate status control.

Weekly actual mileage includes actual distance from executed workouts. Planned
distance remains part of workout data but does not drive the V1 weekly mileage
display or chart.

## Mileage Trend

The Weekly Mileage Trend shows actual mileage only in a 12-week window. Its
navigation is independent from workout-week navigation, can move backward and
forward by one week, and stops at the latest window ending with the runner's
current local week.

Hovering or focusing a chart point reveals that week's exact mileage. The trend
header compares the newest two weeks in the displayed window and reports the
mileage change and, when meaningful, the percentage change. Empty weeks appear
at zero.

## Authentication and Ownership

Clerk provides browser authentication, with Google as the initial social sign-in
provider. The React application attaches the active Clerk session token to API
requests. FastAPI verifies Clerk-issued RS256 JWTs using the configured issuer
and JWKS, including expiry, not-before, and authorized-party validation.

The API derives a provider-neutral current user from the verified token's `sub`
claim. That value becomes the DynamoDB workout owner for reads and writes;
clients cannot submit a different user ID. Read, create, update, and delete
operations are scoped to that owner. Missing workout IDs and IDs owned by a
different user both return `404`.

## Production Architecture

```text
Browser
  ├── Clerk authentication
  └── CloudFront (chosenrunning.com)
        ├── /*      → private S3 frontend
        └── /api/*  → API Gateway → Lambda → Mangum → FastAPI → DynamoDB
```

- CloudFront is the public entry point and uses an Origin Access Control for the
  private S3 frontend bucket.
- API Gateway uses an HTTP API with a Lambda proxy integration.
- Lambda runs the FastAPI service as an ARM64 container image from ECR, adapted
  by Mangum.
- DynamoDB stores workouts in an on-demand table with a user/date index that
  supports per-user range queries and multiple sessions per date.
- ACM supplies the DNS-validated certificate for `chosenrunning.com` and
  `www.chosenrunning.com`; CloudFront uses SNI and the TLS 1.2 (2021) policy.
- Terraform manages application infrastructure, the remote-state bootstrap, and
  the GitHub Actions OIDC role.

## Delivery and Quality

GitHub Actions runs path-scoped checks for the React application, FastAPI
service, container builds, container smoke tests, and Terraform. The web deploy
workflow builds the Vite bundle, syncs it to S3, and invalidates CloudFront. The
API deploy workflow builds and pushes a Lambda image, updates the function, and
checks production health and version endpoints. Application Terraform is
applied through a manually dispatched workflow.

Local validation is exposed through repository Git aliases:

- `git check-web`: ESLint, TypeScript, Vitest, and production build
- `git check-api`: Ruff, formatting, Pyright, and Pytest
- `git check-terraform`: formatting, validation, and plans for both Terraform
  roots

## Known Limitations and Deferred Work

- Production still uses a Clerk development instance. Migration to a Clerk
  production instance is deferred.
- V1 does not implement an editable weekly mileage goal.
- Observability consists primarily of API Gateway access logs, Lambda logs,
  structured request logging, and request IDs. Correlation through every error
  path and frontend error remains incomplete.
- Deployment workflows perform health/version smoke checks, but release revision
  verification and a formal automated rollback workflow are not yet implemented.
- Apple sign-in, native mobile/GPS recording, wearable integrations, training
  blocks, race planning, and richer training-load analytics are deferred beyond
  V1.
